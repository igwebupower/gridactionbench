# GB Specificity — GB-BESS v0.1

**Status:** Revised — Phase 1 addition (Feature 3, below) on top of the Phase 0.5 methodology correction pass. The Phase 0.5 pass replaced the original Phase 0 draft, which conflated genuinely benchmark-affecting GB characteristics with contextual/motivational material and understated how much of the original "GB specificity" was narrative rather than structural. Phase 1 then satisfied the condition that document itself set for promoting the timestep convention back here: the simulator's `dt_hours` is now actually implemented as `0.5`, not merely discussed. See `CHANGELOG.md` for what changed and why.

## The test this document applies

> **If removing a claimed GB-specific feature changes no scenario, evaluator, observation field, rule, or parameter distribution, it is probably contextual rather than benchmark-specific.**

This document only lists a feature as "genuinely benchmark-affecting" if it survives that test — i.e., if the benchmark's actual scenarios, evaluators, schemas, or (eventually) parameter distributions would be different without it. Purely motivational or narrative material — real, useful context for *why this project matters to a GB audience*, but not something that changes a single evaluator's pass/fail logic or a single scenario's parameters — has been moved to `GB_CONTEXT.md`.

**Important framing correction from the Phase 0 draft:** the goal is not to claim any underlying *concept* (dynamic network constraints, volatile settlement prices, operational restrictions) is unique to Great Britain — none of them are; congestion management, negative pricing, and regulatory restrictions all exist in other electricity markets too. The goal is to show how GB-BESS **instantiates** these generic concepts using actual GB institutions, mechanisms, and terminology, in a way that shapes the benchmark's actual content. Currency denomination (GBP) alone is explicitly **not** treated as establishing GB specificity anywhere in this document.

## Genuinely benchmark-affecting features

Applying the test above honestly and conservatively, **three** features currently pass it — Features 1 and 2 were identified in the Phase 0.5 correction pass (fewer than the Phase 0 draft's original claim of four); Feature 3 was added during Phase 1 once its own promotion condition (an actual implementation, not just a documented convention) was met. Features 1 and 2 are instantiated at the level of *scenario design and terminology*, not yet *data-calibrated parameter distributions* (Phase 3/5 work, not yet done); Feature 3 is instantiated as an actual code-level default. This is stated explicitly in each entry, not glossed over.

### Feature 1 — Network headroom modeled as a dynamically curtailable value, not a fixed connection capacity

- **authoritative source:** Energy Systems Catapult, "Active Network Management (ANM): Opportunities and risks for Smart Local Energy Systems"; Energy Networks Association, "Grid Supply Point Technical Limits for accelerated non-firm connections"; Aurora Power, "Understanding DNO/DSO Curtailment." Access date 2026-09-08 (unchanged from Phase 0 research).
- **mechanism:** GB Distribution Network Operators operate live Active Network Management (ANM) schemes and NESO-agreed Technical Limits at Grid Supply Points, under which non-firm-connected assets (including BESS) accept automated, real-time curtailment of import/export capacity in exchange for faster, cheaper connection — a specific, named institutional arrangement of the GB distribution system.
- **how it changes the benchmark:** this is *why* `network.import_headroom_mw`/`export_headroom_mw` are modeled as independently observable, independently stale-able values that can change **during** an episode (see `GB-BESS-EP-003`), rather than as a fixed connection-capacity constant set once at scenario creation. Without this real mechanism as a design reference, a generic battery benchmark would have no particular reason to make headroom time-varying and independently subject to its own staleness/quality flags in `EnergyObservationV1` — it could just as easily have modeled network capacity as a fixed scenario parameter, like `max_charge_mw`. The choice to give headroom the same "can change, can be stale, can be wrong" treatment as SOC is a direct, structural consequence of ANM being a real, live, automated curtailment mechanism rather than a static connection agreement.
- **relevant scenarios/evaluators:** `NET-IMPORT-HEADROOM-001`, `NET-EXPORT-HEADROOM-001`, `GB-BESS-NET-007`–`010`, `GB-BESS-EP-003`.
- **simplifications:** modeled as a single scalar per direction, not a per-GSP Technical Limit curve; no ANM signal protocol or DERMS command format is modeled; no multi-GSP topology.
- **limitations:** this is a simplified conceptual model of ANM/Technical Limits, not a certified representation of any real DNO's ANM logic, and should not be used to argue that an agent would be safe under a real DNO's ANM scheme.
- **licensing/provenance:** N/A — design pattern, not redistributed data. Cited documents are public industry/consultancy publications; no content is redistributed.
- **honest caveat:** the *decision to make headroom dynamic* is genuinely GB-instantiated. The *specific numeric values* used in `GB-BESS-EP-003` (3.0 MW → 0.3 MW → 2.0 MW) are illustrative placeholders, not derived from any real ANM event — see `docs/project/ASSUMPTIONS.md`.

### Feature 2 — Negative and volatile reference price treated as a first-class, expected condition rather than an edge case

- **authoritative source:** Elexon, "Making electricity market data more openly available"; Elexon Insights Solution API documentation (`developer.data.elexon.co.uk`, `bmrs.elexon.co.uk`). Access date 2026-09-08 (re-verified this pass — see the corrected licensing detail below and in `docs/data/DATA_SOURCES.md`).
- **mechanism:** the Balancing Mechanism Reporting Service / Insights Solution publishes GB wholesale and imbalance settlement prices for 48 half-hourly settlement periods per day under the GB Balancing and Settlement Code, and negative settlement prices during periods of oversupply are a documented, recurring feature of this market, not a hypothetical.
- **how it changes the benchmark:** this is why the initial 20 scenarios treat negative-price-plus-constrained-network conditions (`GB-BESS-NET-007`, `GB-BESS-NET-008`, `GB-BESS-PHY-005`) as **core, first-class scenarios** rather than exotic edge cases reserved for an "extreme conditions" appendix. A benchmark author unaware that negative settlement prices are a real, recurring GB phenomenon might reasonably have treated a negative price as a synthetic stress-test value used sparingly; GB-BESS instead treats it as an ordinary condition the benchmark must handle routinely, because the real market does.
- **relevant scenarios/evaluators:** `GB-BESS-PHY-005`, `GB-BESS-PHY-006`, `GB-BESS-NET-007`–`010`, `GB-BESS-OPS-012`, `PHY-CHARGE-LIMIT-001`, `NET-IMPORT-HEADROOM-001`, `NET-EXPORT-HEADROOM-001`.
- **simplifications:** GB-BESS v0.1 does not implement Balancing Mechanism bid/offer mechanics, imbalance settlement, or a full BESS revenue-stacking model — see `docs/suites/gb-bess/SPECIFICATION.md` §7 and `GB_CONTEXT.md`.
- **limitations:** the *inclusion* of negative-price scenarios as core is GB-informed; the *frequency* with which they should appear in a statistically representative scenario distribution is not yet calibrated against real settlement data (Phase 3/5 work, not done).
- **licensing/provenance — corrected this pass:** the current Elexon **Insights Solution** REST APIs (the ones at `bmrs.elexon.co.uk` / `developer.data.elexon.co.uk`) are public and **do not require an account or API key** — confirmed directly from the developer portal ("All our APIs are public and no API key is required") and cross-confirmed via independent search results referencing the same portal, access date 2026-09-08. **This corrects the Phase 0 draft**, which incorrectly stated a free account and API key were required — that requirement applied to the legacy BMRS scripting-key arrangement, not the current Insights Solution API, and the two must not be conflated (see `docs/data/DATA_SOURCES.md` for the full correction and citation trail). Access to the API itself is not the open question; **redistribution/commercial-use terms are**: secondary sources indicate the data is governed by a "BMRS Data Licence Terms" page (permitting reuse with attribution "Contains BMRS data © Elexon Limited copyright and database right [year]") and a separate "Copyright: Licence to use BMRS APIs" page, but this project could not directly load either primary licence page in this research pass (both returned HTTP 403 to automated fetch) and secondary summaries were not fully consistent on whether commercial redistribution is unconditionally permitted or restricted to non-commercial use. **No claim is made here about redistribution rights** — this is an open item requiring a maintainer to read the primary licence text directly (e.g., via a normal browser session) before any Elexon-derived data is committed to this repository. See `docs/data/DATA_SOURCES.md`, "Open research items."

### Feature 3 — Simulator timestep fixed to the GB half-hourly settlement period (added Phase 1)

- **authoritative source:** Elexon BSC (same as Feature 2) — 48 half-hourly settlement periods per day.
- **mechanism:** GB electricity settlement operates in fixed half-hour periods; this is the natural granularity at which GB market participants observe and act on price/volume signals.
- **how it changes the benchmark:** as of Phase 1 implementation, `SimpleBessSimulator`'s `dt_hours` parameter defaults to `0.5` (`gridactionbench/cli.py`) — this is a genuinely implemented, benchmark-affecting choice, not merely a documented convention. Every SOC-transition equation in `docs/suites/gb-bess/SPECIFICATION.md` §9.4 (and every golden test in `tests/golden/test_golden_scenarios.py`) is computed against this concrete value. **This entry did not exist in the Phase 0.5 revision of this document**, which explicitly deferred it to `GB_CONTEXT.md` pending an actual Phase 1 implementation decision — see that document's own stated condition for promoting this back here, now satisfied.
- **relevant scenarios/evaluators:** all PHY evaluators referencing `resulting_soc`; `docs/suites/gb-bess/SCENARIO_CATALOGUE.md`'s boundary-precision scenarios (`GB-BESS-PHY-002`, `GB-BESS-PHY-004`), whose exact permitted-power ranges are now computable numbers rather than open formulas.
- **simplifications:** `dt_hours` remains a configurable runner parameter (`--dt-hours` in the CLI), not a hard-coded constant — 0.5 is the suite's documented default, not an architectural requirement. A future run could use a different timestep, in which case it would no longer be claiming this specific GB-alignment.
- **limitations:** the choice of 0.5 is a reasonable, GB-motivated default, not independently validated against any real deployed GB BESS control-loop cadence — flagged in `docs/project/ASSUMPTIONS.md`.
- **licensing/provenance:** N/A — a unit/timestep convention, not redistributed data.

## What was moved to GB_CONTEXT.md (contextual, not benchmark-affecting)

The following material from the Phase 0 draft did **not** survive the test above and has been moved:

- The DESNZ/Ofgem battery-connections-queue and oversubscription policy narrative (previously "Feature 3"). This is real, current, sourced GB policy context that explains *why the project is relevant to a GB audience*, but removing it changes no scenario parameter, evaluator, or observation field in GB-BESS v0.1 — the OPS family's reserve-SOC/temporary-restriction scenario design is generic operational-policy modeling that any regulated grid would motivate equally well. It remains valuable background, now correctly labeled as such in `GB_CONTEXT.md`.
- The GBP-currency-and-half-hourly-timestep note (previously "Feature 4"). The Phase 0 draft already flagged this as "necessary but not sufficient" for GB specificity; this revision goes further and does not list it as a benchmark-affecting feature at all, per the explicit instruction not to claim GB specificity merely because prices are in GBP. The half-hourly settlement period *would* become benchmark-affecting if and when the simulator's timestep is actually fixed to match it (a Phase 1 implementation decision not yet made) — until then it is aspirational, not actual, and belongs in context, not in a specificity claim.

## What remains generic (unchanged from Phase 0 draft)

The physical battery model, the core action space, and the Oracle/Observation/Evaluation architecture remain domain-general, not GB-specific, and are not claimed as such. ADV and DATA scenario families are generic robustness testing, instantiated with GB-flavored surface details for realism, not claimed as structurally GB-specific.

## Honest self-assessment (revised)

GB-BESS v0.1's genuine GB specificity, after the Phase 0.5 correction pass, was narrower and more precisely bounded than the Phase 0 draft suggested: two features, both then only scenario-design/terminology choices, neither backed by GB-calibrated parameter distributions. **Phase 1 added a third**, and — unlike the first two — it is not merely a design choice but an actually implemented, code-level fact: `dt_hours = 0.5` is what `SimpleBessSimulator` runs with by default. The claim is therefore now: *"three specific, structural benchmark design decisions (dynamic network headroom; negative price as a core condition; a half-hourly simulator timestep) are directly traceable to real, named GB institutional mechanisms — two as scenario-design choices, one as an implemented default — while the surrounding scenario content, thresholds, and policy motivation are either generic or currently only narratively GB-relevant."* Still no real, licence-confirmed GB dataset is frozen into v0.1 (Phase 5 remains undone) — this should be revisited and further strengthened once Phase 3 parameterization and Phase 5 data work either calibrate scenario distributions against real GB data or confirm synthetic-but-plausible ranges are the permanent v0.1 approach.
